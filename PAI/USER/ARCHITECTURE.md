# Архитектурные предпочтения

**Предпочтения Ivan по архитектуре, дизайну систем и паттернам.**

---

## Основные принципы

### Философия дизайна
- Простота над сложностью — YAGNI как принцип жизни
- Intent over Syntax — фокус на результате, не на красоте кода
- Context over Complexity — контекст и семантические связи важнее архитектурного излишества
- Continuous Delivery — быстрые итерации, рабочий MVP
- Fail fast — ошибки видны сразу, не скрыты за абстракциями

### Предпочтения трейд-оффов

| Трейд-офф | Предпочтение | Примечание |
|-----------|-------------|------------|
| Скорость vs Корректность | Корректность | Кроме прототипов — там скорость |
| DRY vs Ясность | Ясность | Дублирование допустимо |
| Гибкость vs Простота | Простота | YAGNI |
| Производительность vs Читаемость | Читаемость | Оптимизировать позже |

## Архитектура кода

### Предпочитаемые паттерны
- **Feature-based модульная структура** — каждый модуль самодостаточен (components, hooks, services, types, utils)
- Server Components по умолчанию, "use client" только для интерактивных
- Чёткие границы между модулями — модуль не лезет в чужие внутренности
- API routes для серверной логики, не API ради API
- Однонаправленный поток зависимостей (Feature-Sliced Design принцип)

### Анти-паттерны (избегать)
- **Спагетти-код** — жёсткие связи между модулями, отсутствие границ
- Over-engineering — не создавать абстракции для одноразовых операций
- Болтовые решения — искать корневую причину, а не добавлять хуки
- God-компоненты — разбивать на мелкие, атомарные
- Магические строки — использовать конфигурацию
- **Микросервисы ради микросервисов** — distributed complexity без реальной необходимости

## Архитектура систем

### Предпочитаемые подходы
- **Модульная архитектура** — чёткие границы модулей, изоляция зависимостей, независимая разработка и тестирование
- **Модульный монолит для веб-приложений** — один деплоймент, но строгая модульность внутри (feature-based modules с собственными components, hooks, services, types)
- **Отдельные сервисы для независимых систем** — Telegram бот, дашборд, API — отдельные проекты, но каждый внутри модульный (не микросервисы ради микросервисов)
- File-based data — парсинг markdown файлов вместо БД для персональных данных
- TCP Socket для health-check (не HTTP fetch — работает с любым протоколом)
- CLI-first — предпочитать CLI инструменты перед GUI

### Обоснование архитектурного выбора (исследование 02.2026)
- **42% компаний** вернулись от микросервисов к более крупным единицам (CNCF 2025)
- **ThoughtWorks** рекомендует модульный монолит как лучшую альтернативу на ранних стадиях
- **Для соло-разработчика с AI** — модульный монолит оптимален: модульность без distributed complexity
- **Личный опыт Ivan** — модульная структура (Agent Zero Telegram бот) проще редактировать и поддерживать чем спагетти-код
- **Правило:** начинать с модульного монолита, извлекать в отдельные сервисы только при реальной боли (масштаб, разные команды, разные циклы деплоя)

### Инфраструктура
- **Compute:** VPS (Timeweb) + Docker контейнеры + WSL2 локально
- **Database:** Supabase (PostgreSQL) для продакшн, файлы для персонального
- **Runtime:** Bun (предпочтительно), Node.js (fallback)
- **Деплой:** Vercel для фронтенда, Docker на VPS для бэкенда

## API дизайн

### Стиль
- REST для простых CRUD операций
- Next.js API Routes (App Router) для BFF
- Версионирование: не нужно для персональных проектов

### Конвенции
- Множественное число для ресурсов (`/api/goals`, `/api/sessions`)
- JSON ответы всегда
- Обработка ошибок: HTTP статус + `{ error: "message" }`

---

## Дизайн данных

### Предпочтения баз данных
- PostgreSQL (через Supabase) для структурированных данных
- Markdown файлы для персонального контекста (PAI USER/)
- JSONL для логов и рефлексий

### Моделирование данных
- Простые схемы — не перенормализовывать
- created_at/updated_at обязательно
- UUID для primary keys в Supabase

## Безопасность

### Аутентификация
- Для личных проектов: не нужна (localhost)
- Для публичных: Supabase Auth

### Защита данных
- SSH ключи единые для всех серверов
- Прокси через Xray VPS для обхода блокировок
- Никаких секретов в коде — .env файлы
