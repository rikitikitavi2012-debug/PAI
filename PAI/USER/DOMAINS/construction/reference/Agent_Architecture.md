# Архитектурные идеи для Construction Orchestrator

Справочный материал, извлеченный из проекта "СТРОЙ-ИНТЕЛЛЕКТ" (Perplexity, 2024).
Не является активной системой -- это набор архитектурных идей для будущей реализации в PAI.

---

## Концепция: 8+1 специализированных агентов

Оригинальная архитектура предполагала команду из 8 агентов + 1 координатор.
Каждый агент -- узкий специалист с четкой зоной ответственности.

### Реестр ролей

| ID | Роль | Архетип | Зона ответственности |
|---|---|---|---|
| Agent_A | Инженер-проектировщик / Нормативный Инспектор | Страж (Guardian) | СП, СНиП, ГОСТ, compliance. Первая линия защиты от юридических и технических рисков |
| Agent_B | Инженер-Сметчик | Оптимизатор (Optimizer) | Расчет материалов, BoM, стоимость. Финансовый мозг проекта |
| Agent_C | Менеджер по Закупкам | Реалист (Realist) | Поставщики, актуальные цены, логистика, доступность материалов |
| Agent_D | Планировщик Проектов | Хранитель Времени (Timekeeper) | Графики, сроки, ресурсы, критический путь |
| Agent_E | Конкурентный Аналитик | Стратег (Strategist) | Мониторинг рынка, ценовое позиционирование, бенчмарки |
| Agent_F | Юридический Консультант | Писарь (Scribe) | Договоры, Градкодекс, разрешения, юридическая чистота |
| Agent_G | Data Watcher (служебный) | Часовой (Sentinel) | Мониторинг обновлений нормативов и стандартов |
| Agent_U | Координатор Проекта | Оркестратор (Orchestrator) | Центральный хаб, интерфейс к менеджеру, эскалация |
| Agent_V | Визуализатор (перспективный) | -- | 3D-рендеры, референсы, визуальное ТЗ для бригады |

## Ключевые архитектурные решения

### 1. Событийная модель (Event-Driven)

Агенты общаются через события, а не прямые вызовы. Каждый агент подписан на определенные события:

- **Agent_A** (Нормативщик): `LeadQualified`, `DetailedSmetaApproved`, `ImpactAssessed`
- **Agent_B** (Сметчик): `LeadQualified`, `PreliminaryEstimateApproved`, `ClientRequestsRevision`, `ImpactAssessed`, `ChangeOrderApproved`
- **Agent_C** (Закупки): `DetailedSmetaApproved`, `GeneratePurchaseOrders`
- **Agent_D** (Планировщик): `LeadQualified`, `FinalizeWorkSchedule`, `ChangeOrderApproved`
- **Agent_E** (Аналитик): `LeadReceived`, `DetailedSmetaApproved`, `LeadLost`, `ProjectPaid`, `OnboardingMetricsCalculated`
- **Agent_F** (Юрист): `ProposalApproved`, `ChangeOrderApproved`
- **Agent_G** (Наблюдатель): `ActivateProjectMonitoring`
- **Agent_U** (Координатор): подписан на **все** события

**Идея для PAI**: события можно реализовать как MCP-tool вызовы или через файловую систему (event log).

### 2. Разделение доступа к знаниям

Каждый агент имеет явно определенные права чтения/записи:

| Агент | Читает | Пишет |
|---|---|---|
| Agent_A | `NORM_*`, `TPL_*` | `compliance_report.txt` |
| Agent_B | `PRICE_*`, `TPL_*`, `NORM_*` | `preliminary_bom.csv`, `Smeta_v*.csv` |
| Agent_C | `PRICE_01`, `PRICE_03` | `Purchase_Orders.csv` |
| Agent_D | `TPL_*`, `Smeta_v*.csv` | `draft_timeline.txt`, `work_schedule_v*.csv` |
| Agent_E | `PRICE_*`, аналитика из всех событий | `benchmark_report.txt`, `Team_Synergy_Report.md` |
| Agent_F | `PROC_05`, Градкодекс, `ФЗ-*` | `Договор.pdf`, `Доп_соглашение.pdf` |
| Agent_U | Все `PROC_*` файлы | -- |

**Идея для PAI**: в системных промптах агентов явно указывать, какие файлы из `construction/` они могут читать.

### 3. Детерминированность vs. обучаемость

Критически важное разделение:

- **Детерминированные** (learning_enabled: false): Agent_A (нормативы), Agent_F (юрист), Agent_G (наблюдатель), Agent_U (процесс)
  - Причина: эти агенты НЕ должны "учиться" обходить нормы или менять юридическую логику
- **Адаптивные** (learning_enabled: true): Agent_B (сметчик), Agent_C (закупки), Agent_D (планировщик), Agent_E (аналитик)
  - Причина: могут улучшать оценки на основе опыта

**Идея для PAI**: при реализации хранить "опыт" адаптивных агентов в отдельных файлах `reference/experience_*.md`.

### 4. Стратегии разрешения конфликтов

- **ESCALATE** -- большинство агентов эскалируют конфликты к Agent_U (координатору)
- **HUMAN_IN_THE_LOOP** -- Agent_U является конечной точкой эскалации, привлекает человека
- **Критические нарушения**: Agent_A при обнаружении нарушения норм -- `TERMINATE_PROCESS` + уведомление координатора

## Персоны и стили общения

Каждый агент имеет "машину состояний" для адаптации тона:

| Агент | По умолчанию | Триггер перехода | Режим |
|---|---|---|---|
| Agent_A | CALM (формальный, точный) | Критическое нарушение нормы | URGENT (директивный, сжатый) |
| Agent_B | SUPPORTIVE (деловой) | Клиент просит пересмотр | CREATIVE (проактивный, альтернативы) |
| Agent_C | CALM (фактологичный) | Проблема с поставкой | URGENT (срочный) |
| Agent_D | CALM (структурированный) | Отклонение > 5 дней | URGENT (фокус на критическом пути) |
| Agent_E | CALM (аналитический) | -- | -- |
| Agent_F | CALM (юридически точный) | -- | -- |
| Agent_G | CALM (безэмоциональный) | -- | -- |
| Agent_U | SUPPORTIVE (конструктивный) | Эскалация | URGENT (четкий, проблемный) |

**Деэскалация**: Agent_B, Agent_D и Agent_U имеют протоколы деэскалации с триггерами на ключевые слова клиента ("дорого", "долго", "не работает").

## Применение в PAI

Эти идеи можно реализовать поэтапно:

1. **Фаза 1**: Один универсальный Construction Agent с доступом ко всей базе знаний
2. **Фаза 2**: Разделение на 2-3 специализированных агента (Нормативщик + Сметчик + Координатор)
3. **Фаза 3**: Полная мультиагентная архитектура с событийной моделью

Текущий статус PAI: соло-разработчик, MVP-first -- начинать с Фазы 1.
